# Meetings Bot — v1 Requirements

**One-liner:** A shadow assistant that joins Google Meet calls alongside you, listens live, answers
only when addressed by name, and grounds every answer in the project directory you hand it.
After the meeting it drops a transcript + notes next to the project.

**Scenario:** You are in the meeting. The bot sits as a second participant (camera off, muted).
Someone says "Hey Saqib's Assistant, what's the current auth flow?" → it speaks a short,
project-grounded answer. Everyone else → silence. After you leave, it writes notes.

---

## 1. Scope

### In scope (v1)
- Google Meet only (join by URL).
- Join via headless Chromium (Puppeteer) as a *named* participant.
- Hearing: Meet's built-in live captions, scraped from the DOM (bot turns captions on itself after joining).
- Speaking: TTS rendered locally, injected by replacing the bot's outgoing WebRTC audio track (muted when idle).
- Brain: Ollama **cloud** models via the local Ollama daemon API (`http://localhost:11434/v1`), model configurable.
- Project context: read-only digest of `--project <dir>` + on-demand file reads between turns.
- Output artifacts: raw transcript + meeting notes written after the call.
- Dry-run/echo modes for development (see §6).

### Out of scope (v1 — non-goals)
- Teams, Zoom (Teams is a v1.1 adapter behind the joiner interface).
- Unattended attendance — you are always in the room with it.
- Speaking unprompted, moderating, or initiating topics.
- Code edits / command execution on the project (read-only, except its own notes).
- Recording other participants' video.

---

## 2. Functional requirements

- **FR-1 Join.** `meetings-bot join --meeting <url> --project <dir>` launches Chromium with a
  persistent profile, joins the Meet within 30s, and appears as a participant with the configured
  display name. Lobby admission: you (present in the call) admit it — no special privileges needed.
  The account used is a dedicated Google account named e.g. "Saqib's Assistant" so the visible
  name matches the wake name. Camera off, mic muted on entry.
- **FR-2 Hear (captions).** After joining, the bot enables captions via the CC button and polls the
  captions DOM continuously. Each caption line is appended to a rolling transcript with timestamp
  and the best-available speaker attribution (Meet attributes caption lines to speakers).
  If captions cannot be enabled, the bot logs a warning, stays silent, and still records whatever
  it can (fallback: WebRTC audio capture → STT is the v1.1 upgrade path, interface reserved).
- **FR-3 Wake detection.** A reply triggers only when the participant's sentence that follows/contains
  the bot's wake names (config: bot display name + aliases, e.g. ["assistant", "saqib's assistant"])
  is addressed to it — direct question, request, or check-in ("are you there?"). Implementation:
  caption line + preceding context window matched against wake phrases; require a question/request
  form, not a bare name mention. Ambiguous → it does not speak; it may ask one short clarifying
  line at most once per ambiguity (config: `allow_clarify: true|false`, default true).
- **FR-4 Brain.** Replies are generated by the configured Ollama cloud chat model with system prompt =
  persona ("Saqib's meeting assistant") + project brief + rolling meeting transcript excerpt.
  Conversation memory within the meeting: keep full transcript in context (Meet calls are short);
  hard cap ~24k tokens with sliding window.
- **FR-5 Project context.** At launch: build a project brief — directory tree (respecting .gitignore,
  depth-capped), README/CLAUDE.md, manifests (package.json etc.), top-level docs — capped in size,
  cached to disk under `~/.meetings-bot/cache/<project-hash>/`. The model may request additional
  reads between turns (tool: read file under project root only, read-only). Requests outside the
  project root are refused.
- **FR-6 Speak.** Reply text → TTS (pluggable provider; v1 ships at least one working provider) →
  16 kHz mono PCM → replace outgoing audio track for the reply duration → re-mute. While speaking,
  caption polling continues but self-transcripts are tagged and excluded from wake detection and
  context (no self-triggering).
- **FR-7 Rate & length discipline.** One reply per wake event; max speaking length default 150 words /
  ~45s audio (config). No back-to-back replies without a new wake event. If two people trigger it
  within 5s, it answers once covering both questions or says one will follow.
- **FR-8 Deference rule.** Questions about *the project* (architecture, status, numbers from docs,
  code specifics) → answer from the brief. Questions about commitments, estimates, approval, or
  "would Saqib prefer X" → short deferral: "That's better answered by Saqib himself — over to you."
- **FR-9 Leave & notes.** On detecting the meeting ended, or via Ctrl+C, the bot writes:
  - `<project>/meeting-notes/NNN-<date>-<slug>.md` — summary, decisions, action items (owner: whoever
    was attributed), Q&A log (each wake event: question → answer).
  - `<project>/meeting-notes/.raw/NNN-transcript.jsonl` — timestamped caption lines.
- **FR-10 Chat fallback channel.** If audio reply fails (TTS/track-swap error), the bot posts the
  answer text into Meet's in-meeting chat instead, and logs the degradation.

## 3. Behavior policy (hard rules)
1. Never speaks unless a valid wake event occurred this turn.
2. Never repeats itself verbatim within one meeting.
3. Never invents project facts — if not in the brief or readable files: "I don't have that in the
   project — I can check the repo after the call" (and it genuinely adds it to the notes follow-ups).
4. No political/personal opinions; no commitments on Saqib's behalf (FR-8).
5. Total participation ceiling (config, default: 15 wake replies or 10 minutes of talk time per meeting).

## 4. Non-functional
- **Latency budget (wake → start of speech):** ≤ 10s (caption lag 1–3s + LLM 2–5s + TTS 1–2s).
- **Reliability:** DOM selector changes = single module to patch (`CaptionSource`); crash-safe
  transcript (append-per-line, fsync per line); unexpected leave → still writes partial notes.
- **Privacy:** transcript and notes stay on disk locally; nothing sent anywhere except the LLM call
  (which includes meeting transcript excerpt — acceptable for cloud models; a "redact" option can come later).
- **Security:** Google credentials live only in the persistent Chromium profile dir; bot never
  touches your personal Google account.

## 5. Interfaces
```
meetings-bot join --meeting <url> --project <dir> [--name "..."] [--headed] [--model <tag>]
meetings-bot config                     # editor for ~/.meetings-bot/config.yaml
meetings-bot rehearse --meeting <url> --project <dir>   # join a test meeting alone
meetings-bot echo <transcript.jsonl>    # replay captions through wake+brain, print answers to console
```
`config.yaml`: wake_names[], bot_name, ollama{base_url, model}, tts{provider, voice}, defer_phrases[],
limits{max_replies, max_talk_seconds, max_reply_words}, allow_clarify.

## 6. Dev/test modes
- **--headed** for debugging DOM selectors.
- **rehearse:** joins a meeting with only you in it — safest way to tune wake detection & voice.
- **echo:** no browser at all — feed a recorded transcript, verify wake detection + LLM answers on CI.

## 7. Milestones
1. **M1 — Joiner:** headless join with persistent profile, typed name, captions auto-on, raw caption
   capture to JSONL. *(Proves FR-1, FR-2.)*
2. **M2 — Brain dry-run:** wake detection + LLM + reply printed to console (echo + rehearse modes).
3. **M3 — Voice:** TTS provider wired, outgoing track swap, self-transcript exclusion.
4. **M4 — Context:** project brief builder + on-demand file reads.
5. **M5 — Polish:** notes writer, rate limits, defer rules, crash recovery, real-meeting pilot.

## 8. Risks & mitigations
| Risk | Mitigation |
|---|---|
| Google flags the automated account | Dedicated account only; human-paced join; persistent profile; never your personal account |
| Meet DOM changes break captions | Isolated `CaptionSource` module; echo mode makes regression tests cheap |
| Caption lag makes replies feel slow → interruption | 10s budget tracked; if exceeded, bot says "one moment" is forbidden — instead it waits for next natural gap |
| Bot hears itself (captions of its own TTS) | Tag self-audio frames; exclude from wake + context |
| Wake word fires on name mentions not aimed at bot | Require question/request form near the trigger; rehearse mode to tune |
| Ollama cloud slow/unavailable | Retry ×2, then chat-channel fallback with apology |

## 9. Open decisions (needed by M3, not before)
1. **TTS provider** — candidates: Piper (fast, local, robotic-ish), Kokoro (local, better quality),
   cloud (ElevenLabs/edge-tts). Quality bar: pleasant enough that colleagues don't hate it.
2. **Dedicated Google account** — you need to create one (e.g. saqib.assistant.x@gmail.com).
3. **Caption language** — default English (US); configurability only if your calls are mixed-language.
